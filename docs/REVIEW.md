# 微信公众号文章聚合与阅读系统 · 需求评审

- 状态：评审完成，技术选型已锁定，待开工
- 评审日期：2026-09-11
- 使用场景：纯个人使用（单用户），部署在自有服务器 + 自有域名

## 1. 需求描述

1. 抓取指定微信公众号每天发布的文章并持久化存储
2. 文章经排版清洗后在前端页面展示（阅读端）
3. 每天生成一份 AI 总结
4. 定时将原文/摘要以邮件发送
5. 提供完整的前后端，管理后台同时适配手机与 PC
6. 公众号不预置，由用户在管理后台自行填入名称

## 2. 功能拆解

| 模块 | 说明 | 优先级 |
| --- | --- | --- |
| 账号管理 | 名称搜索 -> 候选确认 -> 绑定 `__biz`；支持粘贴文章链接绑定作为兜底 | P0 |
| 抓取调度 | 每日定时抓取、手动触发、增量拉取、失败重试、任务日志 | P0 |
| 内容处理 | 正文提取、HTML 清洗、图片本地化、格式归一化 | P0 |
| 阅读端 | 文章流、详情页、按账号浏览、搜索、已读标记 | P0 |
| AI 总结 | 按日生成汇总（DeepSeek），支持重新生成 | P0 |
| 邮件推送 | 收件人配置、邮件模板、定时发送、测试发送、发送日志 | P0 |
| 系统设置 | 数据源配置、LLM Key、SMTP、数据清理与备份 | P1 |

## 3. 范围边界（本期不做）

- 不做多用户 / 多租户，不做权限体系
- 不做对外公开的分享页与内容分发
- 不做小程序与原生 App，移动端用 PWA 替代
- 不做复杂的全文检索排序，先用 `LIKE` 满足个人量级

## 4. 关键风险与应对

### 4.1 文章发现机制（最高风险）

微信没有公开的「按名称查询公众号」与「拉取任意公众号历史文章」官方接口，免费方案不存在长期稳定的公共服务。应对：

- 抓取层抽象 Provider 接口，数据源类型与参数存库，可随时替换实现
- 三条获取路径：源站搜索（自建 RSS 类服务）/ 粘贴文章链接绑定 `__biz` / 手动导入文章链接
- 「已知 URL 抓正文」稳定可行，作为保底能力：即使发现机制失效，手动补录仍可用
- 已接受偶发失效，配套三项：失败告警邮件、账号「最后成功抓取时间」可见、手动兜底入口常驻

### 4.2 版权与合规

- 抓取内容仅供个人阅读
- 邮件默认发送「AI 摘要 + 文章链接」，不群发全文，规避再传播风险
- 页面展示保留原文出处与原文链接

### 4.3 邮件送达

- 163 个人邮箱存在发信频率与日限额，收件人建议先只填自己
- `from` 必须与 SMTP 登录账号一致，否则 163 直接拒发
- 邮件正文使用 table 布局 + 内联样式，保证各客户端渲染
- 正文控制在 102KB 以内，避免被 Gmail 折叠截断

### 4.4 长期维护成本

- 免费数据源失效是已知且已接受的持续维护项，通过 Provider 抽象降低修复成本

## 5. 决策记录

| 决策项 | 结论 |
| --- | --- |
| 仓库形态 | Node + TypeScript monorepo |
| 前端 | Next.js 15 + Tailwind CSS + shadcn/ui（阅读端与管理后台一体，响应式 + PWA） |
| 后端 | NestJS |
| ORM | Prisma |
| 数据库 | MySQL 8（外部队列要求；时间统一按 UTC 存取） |
| 任务队列 | MySQL `job_queue` 表自建（`packages/queue`，无需额外引入 Redis） |
| 抓取 | fetch/undici + cheerio + sanitize-html |
| AI | DeepSeek API（走 openai SDK 兼容协议） |
| 邮件 | nodemailer + 手写 HTML 模板，默认「摘要 + 链接」 |
| 抓取代码组织 | 独立 `packages/wechat`：解析、Provider、POC 脚本 |
| 数据源 | 尽量免费，接受偶发失效 |
| 首次接入回溯 | 3 天（默认值，可手动调整，不写死） |
| 部署 | 自有服务器 + 域名（细节暂缓，先留 docker-compose 骨架） |
| 数据库变更（2026-09） | 由 PostgreSQL 改为 MySQL 8（外部环境要求）；队列随之从 pg-boss 换成 MySQL `job_queue` 表，历史数据已迁移 |
